# ResellBD API Documentation

This document describes the API interactions for ResellBD. The platform communicates primarily with a managed Supabase Postgres backend using the Supabase Javascript Client.

## Authentication APIs (Supabase Auth)

ResellBD utilizes Supabase GoTrue for authentication.

### `signInWithPassword(email, password)`
Authenticates a user and establishes a secure session.

### `signUp(email, password, metadata)`
Registers a new user. The `metadata` object must contain `full_name`. An associated `profiles` row is automatically generated via a Postgres Trigger.

## Marketplace & Products

Products are queried from the `public.products` table.

### Fetch Active Products
```typescript
const { data } = await supabase
  .from('products')
  .select('*, profiles(full_name, avatar_url, rating), categories(name)')
  .eq('status', 'active')
  .order('created_at', { ascending: false });
```

### Search & Filter
Location-based filtering relies on the hierarchical fields `division`, `district`, `upazila`.
```typescript
const { data } = await supabase
  .from('products')
  .select('*')
  .eq('division', 'Dhaka')
  .ilike('title', '%search_query%');
```

## Orders & Payments

### Create Order
Orders are generated by inserting into `public.orders`. The backend utilizes Edge Functions to process Stripe/SSLCommerz payments, but records are stored locally.
```typescript
const { data } = await supabase
  .from('orders')
  .insert({
    buyer_id: currentUserId,
    seller_id: targetSellerId,
    total_amount: calculateTotal(),
    status: 'pending'
  });
```

## Messages & Notifications (Realtime)

ResellBD heavily leverages Supabase Realtime for chat.

### Subscribe to Conversation
```typescript
const channel = supabase
  .channel(`room_${conversationId}`)
  .on('postgres_changes', { 
    event: 'INSERT', 
    schema: 'public', 
    table: 'messages',
    filter: `conversation_id=eq.${conversationId}` 
  }, payload => {
    handleNewMessage(payload.new);
  })
  .subscribe();
```

## Admin APIs

Admins (users with `role = 'admin'` in `profiles`) can access all data via RLS bypass policies or specific Admin views. Audit logs are written automatically via `log_critical_action` triggers.
